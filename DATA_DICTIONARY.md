# Local Blue Books data dictionary

Generated by `build_local_docs.py`; logical build/schema version 10.

## Population contract

Runner Step 5 or Explorer Step 7.3 calls `refresh_local`: validate local inputs, recover saved section bodies, prune only unlinked empty entity sections, import references, normalize pages, parse saved entities and OMIM identifiers, extract codes, mentions, site hints/evidence, then build search documents and FTS. Data replacement is transactional. Runner Step 7b optionally mirrors the managed snapshot with preserved keys/timestamps and verifies normalized row hashes before committing.

Missing reference files fail before clearing data. No online access, login, discovery, or crawling is performed. `requirements-local.txt` lists local processing dependencies; pyodbc and ODBC 17/18 are needed only for SQL Server. The neighboring BBNotebook modules and local reference files are required.

The `.local-build.json` sidecar records reference hashes, build version, UTC time and counts; it is not an agent-activity table. Corpus and reference hashes are checked before mirror; changed inputs require a full local refresh. Native stemming and ranking may differ.

## Term hygiene and indexed derived columns (2026-10-10)

The initial live audit found 674 footnote-suffixed rows in page_icdo_codes, 673 in page_term_mentions (six text/key columns), and 558 in page_entity_evidence in each database. entity_codes and entity_related_terms had no such suffixes, but did contain trailing whitespace/punctuation and citation/cross-reference endings.

The five tables have stored TermUS and TermNormUS columns and separate nonunique 600-UTF-16-unit Unicode lookup indexes in SQL Server (TEXT indexes in SQLite). Overlength keys fail explicitly; no truncation or hash-only substitute is used.

| Table | Authoritative display/key input |
|---|---|
| `entity_codes` | `term` |
| `entity_related_terms` | `term` |
| `page_icdo_codes` | `term_in_coding_section` |
| `page_term_mentions` | `term_original` |
| `page_entity_evidence` | `term_clean` |

`TermUS = UpperInitial(CleanBritishSpelling2(CleanDisplayTerm(source)))`; `TermNormUS = UpperInitial(Clean2(TermUS))`. Clean2 preserves case and NULL; the display layer uppercases only an initial ASCII a-z, never Greek symbols, digits or later letters. Clean2 itself is unchanged. The maintainer selected the currently deployed SQL Server Clean2 v3 as authoritative. 00_dbo_Clean2.sql is its snapshot; clean_term2.py executes that same restricted straight-line replacement program, failing on unsupported syntax rather than drifting. The initial 10,065-input Python/SQL comparison has zero discrepancies after alignment.

CleanTermEnding removes trailing footnotes (dagger, double dagger, asterisk, section/paragraph marks), list punctuation/whitespace, leading bullets and unambiguous `[[citation]]` / `<< see ... >>` tails. Numeric superscripts/subscripts, scientific signs, balanced parentheses and meaningful words remain. Raw HTML, sections, snippets, identifier numbers and code assignments are untouched. The maintainer approved removal of saved-HTML-confirmed misplaced explanatory prose from uncoded entity/related rows. Genuine parenthetical qualifiers remain. Punctuation/prose-only contextual code terms use an unambiguous structured coding/subtype assignment, otherwise NULL; code evidence is retained. No reference/workbook tables showed the audited suffixes. Version 9 capitalizes their initial ASCII letter too, without changing the remaining reference text or legacy key rules.

### Page code-term view (version 10)

#### Deprecated legacy field: `is_subtype`

**Deprecated:** do not use `is_subtype` in new queries, extraction logic, or schema design. It is retained only for backward compatibility and is not an inferred biological classification. Historically, in `entity_codes`, `1` meant the term came from a Blue Books **Subtype(s)** section (including nested subtype sections); `0` meant it came from the ordinary **ICD-O coding** section. `_parse_subtype_block` in the companion `bb_entity_extract.py` set this legacy flag.

For backward compatibility, `v_page_code_terms` still exposes the deprecated field. Entity rows carry the stored flag. Contextual `page_icdo_codes` rows inherit the flag from a matching **page + raw code + TermUS** in `entity_codes`; otherwise they use `0`. Historically, repeated occurrences used `MAX(is_subtype)`. New consumers should use `term_role` and explicit provenance instead.

Recovered alternate terms stored in `entity_related_terms` appear with deprecated `is_subtype=0`, even when recovery metadata has `suggested_qualifier='subtype'`. These describe different things:

| Field | Meaning |
|---|---|
| Deprecated `is_subtype=1` | Legacy flag for extraction from a source subtype section |
| `suggested_qualifier='subtype'` | Proposed relationship for a recovered term |

**Deprecated `is_subtype=0` does not mean a diagnosis is not biologically a subtype.** It means the legacy source-subtype flag was not established by this extraction pathway. See [deprecated `is_subtype` assignment](IS_SUBTYPE_ASSIGNMENT.md) for historical behavior.

#### `terminology_kind` values

`terminology_kind` records where in the source page a term came from. It is provenance only, not code validity, preferred-term, synonym or registry status. There are five atomic values:

| Value | Definition | Origin |
|---|---|---|
| `coding` | Term from the page's ICD-O coding or Subtype(s) section | `entity_codes` |
| `contextual` | Term-code pair found in section text as a page-level code mention | `page_icdo_codes` |
| `acceptable` | Related terminology labeled "Acceptable" by the source | `entity_related_terms.kind='acceptable'` |
| `not_recommended` | Related terminology labeled "Not recommended" by the source | `entity_related_terms.kind='not_recommended'` |
| `other` | Unlabeled related terminology, including recovered alternate terms | `entity_related_terms.kind='other'` |

When one page/edition/code/`TermUS` row has more than one origin, distinct atomic values are combined alphabetically with `; ` (for example `coding; contextual`). Current combined values are `acceptable; coding`, `acceptable; not_recommended`, `coding; contextual`, `coding; other` and `contextual; other`; other sorted combinations can occur after refreshes, so filter with `LIKE` or split on `; `. See [terminology_kind values](TERMINOLOGY_KIND_VALUES.md) for counts.

`candidate_topography_codes` contains distinct page-level site hints with `confidence_score >= 0.9`, alongside `site_confidence_min/max`. These are supporting page hints, not verified term-specific sites or patient assertions. Broad lower-confidence book-family prefixes are excluded. No qualifying hints produce NULL, not an invented site.

`entity_term_code_matches.official_termUS` is a stored, indexed derived display maintained by INSERT/UPDATE triggers. Both editions are US-normalized. The existing match view now projects this as `official_term` and `candidateTermUS`, with the unchanged original reference label in `official_term_source`. The views can be read by plain SQLite connections without registering normalization functions. Writes still require the canonical connection helper, as for other term triggers. `local_pipeline.deploy_term_views(path)` / `bluebooks_local.deploy_term_views(path)` performs a backed-up view-only upgrade and verifies original-field preservation, unique pairs and cross-engine view/table parity. Normal migrations and full refresh install the same definitions.

`term_recovery.dry_run(path)` reports proposed counts without writes. `term_recovery.apply_recovery(path)` makes verified paired database backups, applies the recovery and search documents, then uses the standard validated mirror and checks idempotence. Schema changes and paired engine commits are not a distributed transaction; errors are raised and backups are retained.
